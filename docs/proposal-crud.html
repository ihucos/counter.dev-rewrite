Proposal: consolidate the API into resource CRUD

Backend rewrite · status: proposal

The API is 20 flat @api_view functions that all encode the same few resources as verb-named endpoints. Grouping them into two DRF ViewSets on one router removes most of the hand-rolled plumbing, gives list/create/update/delete for free from the router, and lets the Swagger schema fall out of the serializers automatically.

Misc /feedback /newsletter_register /subscribed /lang Keep as small function views — one-shot actions and lookups, not resources.

What gets deleted

delete_site, delete_user, reset_token, delete_token, set_pref_site, set_pref_range, account_edit, me — 8 endpoints replaced by AccountViewSet (with its nested share_token subresource) and an extended SiteViewSet, all registered on one SimpleRouter. The SPA touchpoints (navbar sign-out, setup page, share panel) need URL + method updates; /lang and the tracker are untouched.

Wins

  • DRF supplies auth, validation, and 404-on-missing-object per method instead of per-function copies.
  • The schema (Swagger docs) is generated from ModelSerializers — almost no @extend_schema maintenance left.
  • HTTP semantics: mutations stop hiding behind GET/POST, so logs, proxies, and the schema reflect what they do.
  • set_pref_site's "site is the raw query string" hack disappears — it becomes a validated model field.

Risks / notes

  • Sessions/guest/demo access still resolves through AccountAuthentication unchanged.
  • Sites stay unique per user, lookup by name with the widened regex — same as today.
  • GET /account replacing /me keeps the 401-means-signed-out contract the SPA relies on.
  • The selected_site/date_range promotion needs a migration plus backfill from the existing prefs values.
  • Effort: mostly mechanical; the frontend fetch layer and tests are the bulk of the diff.
